# Workflow

```
grilling → to-spec → to-tickets → [implement+commit → review] ↻ → final review → done
```

## Dispatch format

Каждый диспатч — компактный промпт из трёх частей:

1. **Навыки** — список через запятую (`tdd, shared-context`). Без пересказа содержимого.
2. **Пути к файлам** — `.scratch/<feature>/spec.md`, `.scratch/<feature>/shared-context.md`, `.scratch/<feature>/tickets/NN-*.md` (`.scratch/` исключён из git). Без содержимого.
3. **Задача** — одно предложение, что сделать и что вернуть.

Запрещено: вставлять содержимое spec/shared-context/tickets в промпт диспатча — субагент прочитает файлы сам.

**Resume по умолчанию:** продолжай сессию существующего субагента (`task_id`) всякий раз, когда работа относится к той же задаче/тикету/этапу — скиллы и файлы уже в его контексте. Свежий диспатч — только при смене этапа или радикальном изменении задачи.

## Subagent reports

Субагент возвращает главному агенту краткий отчёт:
- статус (done / blocked / bugs found)
- изменённые файлы
- что нового добавил в `shared-context.md` (если добавлял)

Запрещено: копировать содержимое файлов в отчёт — это дублирует контекст главного агента.

## Bug Reports

Если пользователь сообщает о баге (вне основного пайплайна):

1. Диспатчить `@general` c навыками `tdd` и `shared-context` — найти причину бага, написать failing test, исправить, закоммитить.
2. Диспатчить `@general` c навыком `review`.

**Найден баг?** → та же логика 4c: проверка user story → fix → re-review. Те же лимиты итераций.

## Shared Context

Файл `.scratch/<feature>/shared-context.md`. См. навык `shared-context` за полными правилами.
- После `to-spec` — убедись, что создан.
- Субагент читает файл с диска сам; передаётся только путь.
- Субагент дополнил — файл уже обновлён на диске, передавать ничего не нужно.

## Pipeline

**Перед началом работы** проверь, есть ли уже `spec.md` и `shared-context.md` в `.scratch/<feature>/`. Если есть — пропускай grilling и to-spec.

### 1. grilling
Идея ещё сырая, есть открытые вопросы? Загрузи навык `grilling` и проведи интервью сам. Цель — достичь shared understanding, закрыть все решения. Если решения уже приняты — пропускай, иди в to-spec.

**Grilling всегда делает основной агент** — грилл не делегируется субагентам.

Итоговые решения на шаге `to-spec` попадут в `spec.md` (секция **Implementation Decisions**).

### 2. to-spec
Диспатчить `@general` c навыком `to-spec`. Результат: `spec.md`, `shared-context.md`.

### 3. to-tickets
Диспатчить `@general` c навыком `to-tickets`. Результат: тикеты в `.scratch/<feature>/tickets/`.

### 4. Implement → Review Loop

Начинай с frontier тикета (все блокирующие уже done).

**Параллелизм frontier-тикетов:** независимые тикеты (непересекающиеся файлы) диспатчь параллельно — несколькими task-вызовами в одном сообщении, каждому свой путь и свой субагент. Ограничения:
- Тикеты не должны трогать одни и те же файлы
- Общий build/test suite одновременно с другим тикетом не запускать; параллельно — только прогон тестов по своим файлам (команду смотри в shared-context)

#### 4a. Implement
Диспатчить `@general` c навыками `tdd` и `shared-context`. Один диспатч = implement + commit (субагент коммитит сам). Не разбивать на два хендоффа.

#### 4b. Review
Диспатчить `@general` c навыком `review`.

#### 4c. Bug Found?

**Найден баг:**

1. Есть ли в spec user story, покрывающая этот баг?
   - **Есть** → повторить 4a → снова review (4b)
   - **Нет** → диспатчить `@general` c навыком `to-spec` дописать user story и обновить spec → повторить 4a → снова review (4b)

2. Итерации: максимум **5 циклов** `review` (4b) → fix (4a) → `review` на один тикет.
   После 5 итераций баги остаются → **стоп, escalate** пользователю.

В циклах 4c — resume сессий (см. «Resume по умолчанию» выше): фикс продолжает сессию implement-субагента (4a), повторный review — сессию review-субагента (4b).

**Review чист:** тикет done. Следующий frontier тикет.

### 5. Final Review
Все тикеты done → диспатчить `@general` c навыком `review` на всю фичу:
- Все user stories покрыты и работают
- Интеграция между тикетами не сломана
- Ни один тест не падает

**Найден баг?** → та же логика 4c: проверка story → fix → re-review (финальный).
Максимум **3 финальных `review`**. Превысили → escalate.

**Финальный review чист:** фича done.
